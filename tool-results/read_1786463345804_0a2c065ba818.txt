     8→## 1. Development Flow
     9→
    10→Every task follows this cognitive sequence — in order:
    11→
    12→1. **Analyze** — Understand the user's request, intentions, and context. What do they want? How do they want it done? No blind guesses.
    13→2. **Research** — Investigate the relevant topic/code before acting. Understand what already exists, what touches what. Look before you write.
    14→3. **Comprehend** — Confirm the whole task is understood. If anything is unclear, ask directly — no hesitation.
    15→4. **Confirm** — For non-trivial changes, confirm your understanding with the user before building. State what you'll do in one line.
    16→5. **No Assumptions** — Never guess. If unclear: ask the user or verify in the codebase. Assumptions are bugs you ship early.
    17→6. **Modular Complexity** — Long/complex task? Split it across multiple files and multiple workflow steps. Keep each piece manageable, documented, and independently understandable.
    18→
    19→> The concrete step-by-step task loop lives in `workflow.md`. This section is the **mindset**; `workflow.md` is the **procedure**.

    23→## 2. Communication & Honesty
    24→
    25→- **Ask as many questions as needed.** Clarify anything unclear directly with the user.
    26→- **Proactively highlight** concerns, limitations, and future risks — before the user discovers them.
    27→- **Guide the user** through problems and constraints plainly.
    28→- **Never sugarcoat.** If a request has an issue, say so directly. Do not blindly agree. Do not follow requests that you can see are flawed without flagging the flaw first.
    29→- **Be honest at all times.** A correct uncomfortable truth beats a polite wrong answer.
    30→- Keep wording **short, simple, to the point**. Tell as much as needed — no more.

    34→## 3. Summary After Completion
    35→
    36→After completing a task, give the user a **short summary**:
    37→
    38→- **Do not exaggerate.** Do not leave out key details.
    39→- Use **proper formatting**: headings, highlights, emojis for emphasis and spacers.
    40→- Use **multiple empty lines** for spacing where one line isn't enough.
    41→- Lead with the **key outcome**. Then what changed. Then what's next.
    42→- Reference file paths, not file contents (the user opens files if they want detail).
    43→- **Test checklist**: After implementing improvements/fixes, ALWAYS provide a **test checklist** the user can follow to verify each fix on their device. Format: grouped by category (e.g. Playback, Error Handling, Episode Switching), each item as a checkbox `[ ]` with a clear description of what to test + what the expected result is. The user tests, reports back (✅/❌/⚠️), and the agent fixes any remaining issues. This closes the feedback loop and ensures nothing is missed.

    47→## 4. Project Structure
    48→
    49→- Keep the project **easy to handle and manage**. Well-documented, well-understood.
    50→- **AGENT-CONTEXT stays updated after every task** so any future AI agent can pick up immediately.
    51→- Build so that **editing one part** only requires understanding that part + its immediate context — not the whole project.
    52→- **All things link together.** Document the relations (comments in code, notes in knowledge files).
    53→
    54→### Folder Layout (canonical)
    55→
    56→**RULE (non-negotiable):** The repo root contains exactly ONE wrapper folder. All four project zones (`AGENT-CONTEXT/`, `APP/`, `DASHBOARD/`, `REFERENCES/`) live INSIDE that single folder — never directly at the repo root. The wrapper folder's name is the project name (e.g. `ANI-KUTA/`).
    57→
    58→```
    59→repo-root/
    60→└── ANI-KUTA/                    ← the SINGLE wrapper folder (only thing at repo root)
    61→    ├── AGENT-CONTEXT/           # agent memory + rules (versioned in repo)
    62→    ├── APP/ani-kuta/            # Android app (Gradle + Kotlin + Compose)
    63→    ├── DASHBOARD/webpage/       # Next.js dashboard (→ GitHub Pages)
    64→    ├── REFERENCES/              # old-kuta + animiru reference repos
    65→    └── .github/workflows/       # CI (NOTE: .github MUST stay at repo root for Actions to detect it — see below)
    66→```
    67→
    68→**Exception for `.github/`:** GitHub Actions ONLY detects workflows at `<repo-root>/.github/workflows/`. So `.github/` stays at the repo root (NOT inside the wrapper folder). This is a GitHub platform constraint, not a choice. The wrapper folder contains the 4 project zones; `.github/` sits alongside the wrapper folder at the repo root:
    69→```
    70→repo-root/
    71→├── ANI-KUTA/                    ← wrapper folder (4 zones inside)
    72→│   ├── AGENT-CONTEXT/
    73→│   ├── APP/ani-kuta/
    74→│   ├── DASHBOARD/webpage/
    75→│   └── REFERENCES/
    76→└── .github/workflows/           # CI (repo-root level — GitHub constraint)
    77→```
    78→
    79→**Why a single wrapper folder:** The user explicitly requires this. It keeps the repo root clean, makes the project self-contained, and simplifies cloning (one folder to open, not four). If you see the four zones directly at the repo root, that's a violation — fix it.

    83→## 5. Code Rules
    84→
    85→- **Split code into multiple files** for development, maintenance, and reuse. Fewest files that make sense — not one giant file, not a file per function.
    86→- **Document with comments**: what lives where, what the relations are. Comments explain *why*, not *what*.
    87→- **One module = one responsibility.**
    88→- Reuse before you write. Look a few files over before implementing.
    89→- No unrequested abstractions (no interface with one impl, no factory for one product). **Exception:** an interface with one impl is OK when a future swap is explicitly planned (e.g. `WatchProgressStore` — was in-memory in Phase 5c, swapped to SQLDelight in Phase WP; or a player-host interface for MPV → ExoPlayer swap).
    90→- Mark deliberate simplifications with a `ponytail:` comment naming the ceiling + upgrade path.
    91→- **Player lifecycle scaffolding is NOT boilerplate.** `DisposableEffect`s (keep-screen-on, immersive mode, app-exit pause/resume), watchdogs (switching timeout, fatal-error, auto-hide controls), and periodic progress saves are load-bearing per ADR-025 + D-049. Do not delete them as "unnecessary complexity" without explicit user confirmation.

   106→## 7. Architecture
   107→
   108→- **Highly modular.** Multiple things → multiple modules.
   109→- **UI and backend logic are separate per screen.** A screen's UI and its data/logic live in different files/modules. The UI either calls for data or receives it pre-loaded.
   110→- **Frontend (UI)** renders data, handles input only. No data-fetching logic baked in.
   111→- **Backend (data)** fetches, processes, stores. Exposes clean interfaces to the UI.
   112→- They communicate via **defined contracts** (interfaces/repositories), so UI can be customized without touching data logic.
   113→- **Player screen carve-out (ADR-025):** The watch page is exempt from strict UI/backend separation due to the single-MPV-instance constraint. The screen composable owns the MPV view cache + event bridge + lifecycle effects; a `PlayerStateHolder` (plain class, NOT ViewModel) holds observable state; a `PlayerObserver` decouples MPV events via a Callback interface. This is the old project's proven pattern (D-044). The watch page's *surrounding* UI (top nav bar, episode list, episode details) SHOULD still be split into separate composables for customizability — only the player surface + its controls + the MPV lifecycle stay coupled.
   114→
   115→> Concept diagrams + module graph live in `knowledge/architecture.md`. This section is the **rule**; that file is the **design**.

   119→## 8. GitHub Actions & Branching
   120→
   121→- **Always use GitHub Actions** for builds (APK + dashboard). Never build locally.
   122→- **Create a branch** for each feature/fix: `feature/<name>`, `fix:<name>`, `docs/<name>`.
   123→- **Merge to `main` only after** the feature is verified working and satisfactory. Not before.
   124→- Commit messages: Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`, `refactor:`).
   125→- Never force-push to `main`.
   126→
   127→### Build Rules (APK)
   128→- **NEVER** build the APK locally. GitHub Actions only.
   129→- **NEVER** install the Android SDK, JDK (with javac), or any Android build tooling in the local environment. The local environment does NOT have these and MUST NOT acquire them. GitHub Actions provides everything needed.
   130→- **NEVER** run `./gradlew compileDebugKotlin`, `./gradlew assembleDebug`, or ANY Gradle build task locally. Not even for "just checking compilation". Not even for "just finding the error".
   131→- **NEVER** write `sdk.dir=...` to `local.properties`. Do not create `local.properties` at all.
   132→- **How to find compile errors WITHOUT building locally:**
   133→  1. Read the code carefully, line by line, checking every import, type, and API call.
   134→  2. Use sub-agents (Explore type) to review the code for compile errors — they can read files and compare against reference code.
   135→  3. Cross-reference against the OLD project (in `REFERENCES/old-kuta/ANIKUTA/`) which compiles successfully.
   136→  4. Cross-reference against the Animiru documentation (in `REFERENCES/animiru/documentation/`).
   137→  5. Push to CI and read the failure annotations from the GitHub API (`/repos/{owner}/{repo}/check-runs/{id}/annotations`).
   138→  6. Iterate: fix → push → read CI annotations → fix again. This is the ONLY loop.
   139→- **ONLY** `arm64-v8a` + `armeabi-v7a` ABIs. No x86/x86_64.
   140→  - Set in `APP/ani-kuta/app/build.gradle.kts` (`ndk.abiFilters`).
   141→  - Verified post-build in CI (fails on any forbidden `lib/<abi>/`).
   142→- App ID: `com.confused.anikuta`.

   208→## 15. Session-End Backup (Push to GitHub) + Sandbox Recovery
   209→
   210→- ⚠️ **This environment can clear out randomly.** Work not pushed to GitHub can be lost.
   211→- **Every session MUST end with all changes committed and pushed to GitHub.** No exceptions.
   212→- Before declaring a session done: `git status` must be clean, `git push` must be done.
   213→- If the environment was cleared and re-cloned at session start: read `memory/progress.md` first to know where things stand, then continue.
   214→- This rule exists because the environment is ephemeral; GitHub is the source of truth.
   215→
   216→### Sandbox Recovery (if the environment feels off)
   217→
   218→- **If anything feels off** — missing files, broken imports that were previously fine, stale state, weird build errors that shouldn't exist, or the working tree doesn't match what `progress.md` says — **STOP and re-clone the repo from GitHub.** Don't try to patch over a corrupted environment.
   219→- **How to re-clone:**
   220→  1. Move the current (suspect) working dir aside: `mv /home/z/my-project /home/z/my-project.suspect`
   221→  2. Clone fresh: `git clone https://github.com/testplay-byte/ANI-KUTA.git /home/z/my-project` (the repo's default branch IS the wrapper folder structure per §4 — clone into a temp dir first if needed, then move the wrapper folder to the expected location).
   222→  3. Verify `AGENT-CONTEXT/memory/progress.md` exists + matches the last known state.
   223→  4. If the suspect dir had uncommitted work, diff it against the fresh clone + manually port any salvageable changes.
   224→- **Why re-clone instead of patch:** The sandbox can silently delete or corrupt files. Debugging a corrupted environment wastes hours. A fresh clone takes 30 seconds and guarantees a known-good state. GitHub is the source of truth — trust it over the local filesystem.
   225→- **Prevention:** Push frequently (not just at session end). If you complete a major fix, push it immediately. Don't accumulate uncommitted work.

   274→## 20. Filtered Console Logging
   275→
   276→- **Proper console logging for everything.** Every significant action, state change, error, and network call must be logged with enough context to understand what happened and where.
   277→- **Filtered**: Use log levels (VERBOSE / DEBUG / INFO / WARN / ERROR). Logcat tags per module (`Anikuta:Core:Database`, `Anikuta:Feature:Watch`, etc.). The user/developer can filter by tag + level.
   278→- **Toggleable**: Logging can be turned OFF for performance (release builds). Controlled by a build config flag (`BuildConfig.DEBUG` default) + a runtime toggle in Settings for beta/debug builds.
   279→- **What to log**:
   280→  - ✅ INFO: screen navigation, user actions (tap, search), feature start/end.
   281→  - ✅ DEBUG: repository queries, cache hits/misses, state transitions, DI module init.
   282→  - ✅ WARN: recoverable errors (retry, fallback), deprecated API usage.
   283→  - ✅ ERROR: exceptions, failed network calls, DB errors, with stack traces.
   284→  - ✅ VERBOSE: detailed flow tracing (only when debugging a specific issue).
   285→- **What NOT to log**: user credentials, tokens, personal data, full request/response bodies (log URLs + status codes only).
   286→- **Implementation**: Use a central `Logger` wrapper (in `:core:common`) that respects the level + tag + toggle. Never call `Log.d()` directly — always go through `Logger`.
   287→- **Performance**: When logging is OFF, the Logger is a no-op (zero overhead). Use `if (Logger.isEnabled)` guards around expensive log message construction.
   288→- **Logcat filter format for Android Studio**: When giving the user a logcat filter to diagnose an issue, ALWAYS use this format (directly pasteable into Android Studio's Logcat filter bar):
   289→  ```
   290→  tag:Anikuta:Feature:Details | tag:Anikuta:Feature:Watch | tag:Anikuta:Core:Player:Observer message~:(?i)(keyword1|keyword2|keyword3)
   291→  ```
   292→  Rules:
   293→  - Use `tag:` prefix for each tag, separated by ` | ` (space-pipe-space).
   294→  - Add `message~:(?i)(keywords)` to filter by message content (case-insensitive regex). List keywords separated by `|` inside the group.
   295→  - NEVER use `adb logcat` commands — the user uses Android Studio's Logcat panel, not the command line.
   296→  - Replace the tags + keywords with the ones relevant to the issue being diagnosed.

   327→## 22. UI / UX Quality — Buttery Smooth Animations
   328→
   329→> The user is a great fan of rich, buttery-smooth animations and beautiful, minimalistic UI. This is a quality bar, not an afterthought.
   330→
   331→### Animation Requirements
   332→- **Scrolling**: smooth scroll effects (parallax, fade-in on scroll, collapsible headers that animate). Never janky.
   333→- **Screen transitions**: animated screen switches (fade, slide, shared element transitions where appropriate). Never instant cuts.
   334→- **Button clicks**: MUST give user feedback — ripple, scale-down on press, color change, haptic. Never a dead tap.
   335→- **Loading states**: smooth skeletons / shimmer, not jarring spinners where possible.
   336→- **State changes**: animate UI state changes (expand/collapse, appear/disappear) — never pop in/out.
   337→
   338→### Design Aesthetic
   339→- **Simple, minimalistic, good-looking.** Not cluttered. Every element earns its place.
   340→- **Follow `APP/ani-kuta/DESIGN-LANGUAGE.md` strictly.** It captures the old project's proven aesthetic (lime accent, warm darks, translucent cards, floating pill nav, scroll blur).
   341→- **The design language is a living document.** When the user mentions UI improvements, update `DESIGN-LANGUAGE.md` AND propagate to the code.
   342→
   343→### Performance
   344→- **60fps target.** Animations must not drop frames. Use Compose's animation APIs correctly (`AnimatedVisibility`, `animateContentSize`, `SharedTransitionLayout`).
   345→- **No heavy work on the main thread** during animation. Offload to IO/background.
   346→- **Test on low-end devices** (not just emulators).

   350→## 23. Live Data Verification
   351→
   352→> When the user makes a change, it must be verified AND reflected live on screen. No "change + manual refresh."
   353→
   354→### Rules
   355→1. **Every user action has immediate visual feedback.** If the user taps "Add to Library," the UI updates instantly (optimistic update), then confirms with the backend.
   356→2. **Data changes propagate live.** Use `Flow`/`StateFlow` throughout. The UI observes state and recomposes automatically. Never poll.
   357→3. **Verify changes persisted.** After a write, verify it landed (read-back or DB callback). If it failed, roll back the optimistic update + show an error.
   358→4. **No silent failures.** If a save fails, the user MUST know. Toast/snackbar with the error + retry option.
   359→5. **Cross-screen consistency.** If the user adds an anime to their library on the Details screen, the Library screen must reflect it without a manual refresh (shared state via Flow).
   360→
   361→### Implementation
   362→- Repositories return `Flow<T>` for reads (reactive).
   363→- Writes return `Result<T>` (success/failure) — handle both in the ViewModel.
   364→- ViewModels expose `StateFlow<UiState>` — UI collects and renders.
   365→- Optimistic updates: update the UI state immediately, then confirm with the backend. Roll back on failure.

   436→## 27. Tool Failure Recovery (Stop After 5 Tries)
   437→
   438→> When a tool (Bash, Read, Edit, etc.) fails repeatedly, hammering it wastes context and time. The environment often self-recovers if you pause.
   439→
   440→### Rules
   441→1. **Stop after 5 consecutive failures** of the same tool with the same/similar error. Do NOT keep retrying — it won't help and burns context.
   442→2. **Acknowledge the failure to the user** — tell them the tool is erroring and you're pausing. The user may need to reset the session or wait.
   443→3. **Do NOT retry in a tight loop.** After the 5th failure, stop calling that tool entirely for the rest of the turn. Move to a different tool or describe what you would have done.
   444→4. **The environment often self-recovers.** If the user says "continue" or sends a new message, try the tool again — it may work now.
   445→5. **Log the failure** in `lessons-learned.md` with the `[PATTERN]` tag if it recurs across sessions (e.g. "Bash fails after long sessions — context limit or sandbox issue").
   446→6. **If a critical action is blocked** (e.g. can't `git push`), tell the user explicitly: "I can't push to GitHub right now because Bash is failing. The changes are saved locally. Please retry in a new message or run `git push` manually."

   450→## 28. Log Comparison Debugging (When Stuck in Circles)
   451→
   452→> When debugging a feature that "should work but doesn't" — and you've been going in circles for multiple sessions — **stop guessing and compare logs line-by-line** between the working reference and the broken implementation.
   453→
   454→### Rules
   455→1. **Ask the user for logs from BOTH projects.** One log from the working (old) project, one from the broken (new) project. Same scenario, same video, same extension.
   456→2. **Compare the exact sequence of events.** Don't skim — list every event/error/warning in order for both projects, side by side. The difference is the bug.
   457→3. **Look for MISSING events, not just extra ones.** If the old project fires `FILE_LOADED` but the new project fires `FILE_ERROR` + `PLAYBACK_RESTART` — the missing `FILE_LOADED` is the root cause. The `PLAYBACK_RESTART` is the fallback.
   458→4. **Don't assume your code is correct.** Even if sub-agents confirmed "the code is correct," the code may be correct BUT the prerequisite (FILE_LOADED) never fires. The code is right, the trigger is wrong.
   459→5. **Handle fallback events.** If event A doesn't fire but event B does (and B means the same thing), handle event B as a fallback for A. Example: `PLAYBACK_RESTART` (17) as a fallback for `FILE_LOADED` (11).
   460→6. **Don't go in circles.** If you've tried the same fix approach 3+ times and it doesn't work, you're fixing the wrong thing. Step back, get logs from both projects, and compare. The answer is in the diff.
   461→7. **Document the root cause.** Once found, log it in `lessons-learned.md` with the `[PATTERN]` tag. Future agents should not repeat the same circle.

   465→## 29. Crash Handling (Global Safety Net)
   466→
   467→> The app MUST NOT silently crash to the home screen. Every uncaught exception shows a user-facing error screen with copyable logs.
   468→
   469→### Rules
   470→1. **Global crash handler installed in `Application.onCreate()`** — `Thread.setDefaultUncaughtExceptionHandler(AnikutaCrashHandler(this))`. Installed FIRST, before any other initialization (Logger, Koin, Injekt).
   471→2. **Crash report persisted to `filesDir/last_crash.txt`** — survives the process restart so `ErrorActivity` can read it.
   472→3. **`ErrorActivity` launched with `NEW_TASK | CLEAR_TASK`** — replaces the crashed process with a fresh one showing the error screen.
   473→4. **Error screen shows:** error icon + "Something went wrong" heading + explanation + scrollable monospace crash log + Copy button + Restart button + Close button.
   474→5. **Copy button** copies the full crash report (timestamp, thread, device info, exception, stack trace) to the clipboard.
   475→6. **Restart button** clears the crash report + launches `MainActivity` fresh.
   476→7. **Close button** clears the crash report + finishes the activity.
   477→8. **`ErrorActivity` registered in AndroidManifest** — `android:exported="false"`, same theme as `MainActivity`, `configChanges` to prevent recreation.
   478→9. **Ported from the old project** — `AnikutaCrashHandler.kt` + `ErrorActivity.kt` in `app/src/main/java/.../error/`.

   482→## 30. Debug-Build Schema Freedom
   483→
   484→> The project is currently in **debug builds only**. There are no production users. There is no published APK. This gives us freedom to make complete schema changes without migration concerns.
   485→
   486→### Rules
   487→1. **Debug builds can rebuild the schema freely.** You CAN drop tables, add columns with NOT NULL, add CHECK constraints, change column types, restructure relationships — without writing migration scripts. The simplest approach (if a schema change is complex) is to bump the DB version + let SQLDelight recreate the tables. Existing dev-install data will be wiped — that's acceptable for debug builds.
   488→2. **No migration scripts needed for debug.** The `DatabaseDriverFactory.onOpen` migration pattern (ALTER TABLE + hasColumn checks) exists for PRODUCTION. For debug, you can skip it and just let `CREATE TABLE IF NOT EXISTS` handle fresh installs. If a dev install has stale schema, the user clears app data — that's the debug workflow.
   489→3. **When publishing approaches**, the user will explicitly tell you. At that point, you MUST write proper migrations (`.sqm` files or onOpen ALTERs) for every schema change that affects existing data. Do NOT assume publishing is imminent — wait for the user's signal.
   490→4. **SQLite version constraints still apply** (e.g., UPSERT requires 3.24+; API 24-28 ships 3.9-3.22). The debug freedom doesn't change the SQLite version on the device — it just means you don't need to preserve existing data.
   491→5. **CHECK constraints CAN be added** on debug builds (via table rebuild or fresh schema). The "can't ALTER TABLE to add CHECK" limitation is a SQLite constraint, not a project rule — work around it by recreating the table if needed.
   492→6. **This rule supersedes any "preserve existing data" guidance** in earlier decisions when the project is still in debug. Once the user signals production approach, this rule is suspended + migration discipline returns.
   493→
   494→### Why this rule exists
   495→Previous sessions deferred schema improvements (CHECK constraints, UPSERT migration, table restructuring) because "can't ALTER TABLE on existing installs." That's a production concern, not a debug concern. The user explicitly confirmed: debug builds can make complete changes. Don't let migration fear block schema quality during debug.
