## 1. Architecture overview

Hermes-Agent is a personal AI agent with one shared agent core serving many entry points. Shape (from `website/docs/developer-guide/architecture.md`, `AGENTS.md`, and code):

- **Entry points:** interactive CLI (`cli.py`), messaging gateway (`gateway/run.py` + 25+ platform adapters: Telegram, Discord, Slack, WhatsApp, Signal, ...), terminal TUI (`ui-tui/` Ink app speaking newline-delimited JSON-RPC over stdio to a Python `tui_gateway` backend), Electron desktop app (`apps/desktop/`, same JSON-RPC backend), ACP adapter for IDEs, batch runner, API server.
- **Core:** `AIAgent` (`run_agent.py`) - a synchronous conversation loop: build system prompt -> LLM call -> if tool_calls, dispatch via `model_tools.handle_function_call()` and append results -> repeat until final text, bounded by `max_iterations` (default 500) and a token/iteration budget. Messages follow OpenAI format; three API transports (chat_completions, codex_responses, Anthropic Messages) behind one resolver.
- **Prompt assembly (`agent/system_prompt.py`, `agent/prompt_builder.py`):** ordered tiers `stable` -> `context` -> `volatile`. Memory blocks are injected into the **volatile** tier as a **frozen snapshot captured once at session start**; mid-session memory writes persist to disk but never mutate the prompt (prompt-prefix-cache preservation is a stated design invariant: no mid-conversation system prompt rebuilds, toolset swaps, or past-context mutations except compression).
- **Tool layer:** central registry (`tools/registry.py`); each `tools/*.py` self-registers at import time (auto-discovery); ~70+ tools across ~28 toolsets; tools can be gated by `check_fn` availability predicates; a "Footprint Ladder" policy keeps new core tools rare in favor of skills/plugins/MCP.
- **Persistent memory (the piece ACUTE-CODE cares most about):**
  - Two markdown stores on disk under `~/.hermes/memories/`: `MEMORY.md` (agent notes, 2,200-char cap ~800 tokens) and `USER.md` (user profile, 1,375-char cap ~500 tokens). Entries delimited by a `§` line separator; entries may be multiline.
  - One `memory` tool with actions `add` / `replace` / `remove` (+ an atomic `operations` batch mode validated against the *final* budget in one call). No `read` action - content is injected into the prompt. `replace`/`remove` target entries by short unique substring, erroring if the substring matches multiple distinct entries.
  - **Write triggers (who writes, when):** (1) the agent writes proactively during turns, nudged by the system prompt every N user turns (`memory.nudge_interval`, default 10); (2) after every turn, an optional **background self-improvement review** (`agent/background_review.py`) forks a review agent on a daemon thread - it replays the conversation snapshot with a tool whitelist limited to memory + skill tools and asks "should anything be saved or updated?"; it can run on a cheaper auxiliary model with a conversation digest; (3) an optional **write-approval gate** (`memory.write_approval`) stages writes for human review (`/memory pending|approve|reject`), including background writes tagged `[auto]`.
  - **Caps and consolidation:** char limits (not tokens - model-independent). On overflow the tool returns an error listing current entries and instructs the model to consolidate (merge/remove) and retry in the same turn; a per-turn failure cap (3) eventually returns a terminal "save skipped" so memory side effects never block the user reply.
  - **Dedupe/staleness:** exact-duplicate rejection on add, order-preserving dedupe on load. No automatic staleness decay for memory - consolidation is model-driven under the cap pressure. (Skill staleness is handled separately by the Curator, below.)
  - **Safety:** every write and every snapshot-loaded entry is scanned against a shared threat-pattern library (prompt injection, credential exfiltration, invisible Unicode); hits are blocked at write time and replaced with `[BLOCKED: ...]` placeholders in the prompt snapshot (originals stay visible on disk for the user to delete).
  - **User-editable-file guards:** read-modify-write under a lock file + atomic temp-file rename; **external drift detection** - if the on-disk file no longer round-trips through the tool's parser/serializer (manual edit, shell append, patch tool), the mutation is refused and a `.bak.<ts>` snapshot is taken; unreadable-file states abort rather than being treated as empty (anti-wipe guards).
  - **SQLite role:** sessions/messages live in SQLite (`~/.hermes/state.db`, `hermes_state.py` SessionDB) with FTS5 full-text search and session lineage; memory itself is markdown-on-disk, *not* SQLite. `session_search` gives unlimited cross-session recall on demand (raw messages, ~20ms FTS5 queries) complementing the ~1,300-token always-in-context stores. A custom native FTS5 tokenizer for CJK ships under `native/fts5_cjk`.
  - **Pluggable backends:** `MemoryProvider` ABC (`agent/memory_provider.py`) orchestrated by `agent/memory_manager.py`; 8 bundled external providers (Honcho, Mem0, Supermemory, Hindsight, ...) that run *alongside* built-in stores, never replacing them. [UNVERIFIED in depth: individual provider implementations.]
- **Skills system:** skills are markdown `SKILL.md` documents (YAML frontmatter: name, description <=60 chars, version, platforms gating, optional config declarations) in `~/.hermes/skills/` with progressive disclosure: level 0 index (~name/description list), level 1 full skill, level 2 specific reference files - so cost is paid only when content is actually loaded. Skills are also slash commands (injected as a *user message*, never a system-prompt mutation, to preserve caching). **Self-created skills:** the agent authors its own skills via a `skill_manage` tool (create/patch/edit/delete/write_file/remove_file; patch preferred for token efficiency), with hard frontmatter validation, a content scanner on agent-created writes, and provenance tracking (`created_by: "agent"`). A background **Curator** tracks per-skill usage telemetry (use/view/patch counts, last activity), auto-transitions active -> stale -> archived after configured idle/stale windows, archives (never deletes) to a restorable `.archive/`, pins exempt, and only ever touches agent-created skills. Hub installs from registries go through security scanning with trust levels and content-hash provenance.
- **Other subsystems:** delegation (`delegate_task` subagents with leaf/orchestrator roles, spawn-depth cap), cron scheduler (agent-scheduled jobs; cron sessions skip memory by default), kanban multi-agent board, context compression, plugin systems (general hooks, memory providers, context engines, model providers).

## 2. Tech stack

- **Language/runtime:** Python 3.11-3.13 (`requires-python = ">=3.11,<3.14"` in `pyproject.toml`); TypeScript/Node for the Ink TUI (`ui-tui/`) and Electron desktop app (`apps/desktop/`).
- **LLM client:** OpenAI SDK v2 as the primary client, with three transport modes (OpenAI chat-completions, Codex/Responses, Anthropic Messages) plus provider plugins; auxiliary LLM client for side tasks (titles, vision, background review) with per-task model overrides.
- **Storage:** SQLite via Python stdlib with FTS5 (sessions, messages, full-text search; custom C FTS5 tokenizer extension for CJK); plain markdown files for memory and skills; YAML config (`config.yaml` for all behavior, `.env` for secrets only); JSON for cron jobs and pending-write staging.
- **CLI/TUI:** Rich (banner/panels) + prompt_toolkit (input) for classic CLI; Ink (React) terminal UI with a Python JSON-RPC gateway; xterm.js in the web dashboard.
- **Packaging/quality:** uv with exact-pinned dependencies (supply-chain policy after the litellm compromise and a May 2026 npm-worm campaign), `uv.lock`, pytest suite (~17k-25k tests per different docs; large either way), per-file subprocess test isolation, Docusaurus docs site.
- **Notable:** no Vercel AI SDK, no Drizzle, no Tauri - Hermes is Python-first with TS only at UI edges. Relevant contrast for ACUTE-CODE: Hermes keeps *all* state ownership (SQLite, memory files, skills) inside one Python process per profile; ACUTE-CODE splits that between a Tauri shell and a Node sidecar.

## 4. Top 2-3 patterns worth adopting for ACUTE-CODE (what / why / how it maps)

**Pattern 1 - Bounded, file-backed memory with frozen-snapshot injection (maps to FR-8xx core).**
- *What:* Small number of plain-markdown memory stores with hard character caps; entries joined by a unique delimiter; full contents rendered into the system prompt **once at session start** as a frozen snapshot with a usage header (`[67% - 1,474/2,200 chars]`); mid-session writes persist to disk immediately but do not touch the prompt; tool responses reflect live state; a separate unlimited on-demand recall path (FTS5 over session history) handles "what did we say about X".
- *Why:* It resolves the three hard problems at once: bounded context cost (caps force curation instead of unbounded growth), prompt-cache friendliness (stable prefix per session - directly compatible with Vercel AI SDK prompt caching in our sidecar), and user editability (the store is a plain markdown file a human can open and edit). The usage-percentage header is a cheap, clever nudge that makes the model manage its own capacity.
- *How it maps:* ACUTE-CODE per-agent memory = markdown notes on disk + SQLite index owned by the sidecar. Adopt: two-tier store shape (agent-notes vs user/persona profile per agent), char caps with in-prompt usage headers, frozen-snapshot injection per session/agent activation, delimiter-separated entries for lossless round-tripping, and a session-search tool over the sidecar's SQLite transcript index as the unlimited recall tier instead of inflating always-on memory.

**Pattern 2 - Consent-aware write-trigger architecture (who writes memory, and who can say no).**
- *What:* Three coordinated write paths: (a) in-turn agent writes nudged every N user turns; (b) a post-turn background review that replays the conversation with a tool whitelist limited to memory/skill tools and decides what is worth persisting (optionally on a cheaper model, with a digest replay to cut cost); (c) an opt-in staging gate where every write - especially automatic ones - is queued for human approve/reject with `[auto]` tagging, plus threat-pattern scanning of anything that will be injected into prompts.
- *Why:* Memory quality is a write-trigger problem more than a storage problem. Foreground nudges capture context-rich moments; the background fork captures lessons the in-loop agent is too busy to write; the approval gate answers "the agent saved a wrong assumption about me" without disabling learning. The strict scan-before-injection is essential because memory is a prompt-injection vector that persists across sessions.
- *How it maps:* ACUTE-CODE memory policy engine: per-agent nudge interval; a sidecar-side post-turn review pass (cheap model) proposing memory writes; a UI review queue (staged writes in SQLite) with approve/reject; reuse the scan-before-accept idea for any content that will be injected into agent context. The per-turn consolidation-failure cap ("memory side effects must never block the reply") is a directly portable behavioral rule.

**Pattern 3 - Skills as governed procedural memory with a lifecycle (maps to our v1 skills + future self-created skills).**
- *What:* Skills are plain `SKILL.md` files with strict minimal frontmatter (short description, platform gates) loaded with progressive disclosure (index -> full -> referenced file). The agent creates/patches its own skills through one tool with hard frontmatter validation and a content scanner; provenance (`created_by: agent`) is recorded; a background Curator uses per-skill usage telemetry to transition unused agent-created skills to stale then archived (never deleted, always restorable, pins exempt) - and never touches human-authored or hub-installed skills.
- *Why:* Self-created skills without governance rot fast (duplicates, stale procedures, hallucinated steps). Hermes' answer - telemetry-driven, non-destructive, provenance-bounded maintenance - is the minimal credible governance loop, and progressive disclosure keeps a growing skill library from inflating every prompt.
- *How it maps:* ACUTE-CODE v1: markdown skills in a per-workspace/per-agent directory with the same frontmatter discipline and three-level disclosure (index in system prompt, full body on invocation). Future self-created skills: record `created_by` provenance, log usage counts in the SQLite index, and run an idle-based archive (not delete) pass over agent-created skills only. The "inject skill content as a user message, not a system-prompt edit" invocation trick carries over directly to cache-stable sessions in the AI SDK.

## 5. What to avoid and why

- **God-files.** `run_agent.py` ~12k LOC, `cli.py` ~11k LOC, `hermes_state.py` ~15k LOC / ~590KB; their own AGENTS.md begs contributors to split them. ACUTE-CODE's sidecar should keep focused modules from day one; extraction later is expensive.
- **Core-tool sprawl.** 70+ tools across 28 toolsets, every tool schema shipped on every API call. Hermes' own "Footprint Ladder" policy exists to *stop* this. For ACUTE-CODE: keep the per-agent core toolset small; push capability into skills/MCP/sidecar REST endpoints.
- **Single-writer-per-home memory assumption.** Hermes explicitly warns "one agent per Hermes home" - two writers compound each other's entries; their drift guards exist because even one human editor breaks round-tripping. ACUTE-CODE is *multi-agent by design*: per-agent memory scoping, per-store file locks, and drift-safe merge behavior must be first-class, not retrofitted.
- **Prompt-cache doctrine leaking into product complexity.** "Cache is sacred" produced deferred-invalidation flags, `--now` opt-ins, ContextVar plumbing for config snapshots, and a frozen-memory UX where writes only appear next session. Adopt the principle (stable prefixes via AI SDK cache semantics) but decide explicitly where ACUTE-CODE accepts a cache break (e.g., memory refresh between tasks) instead of inheriting the full invariant machinery.
- **Docs/README drift.** README claims session search uses "LLM summarization"; the memory doc says raw messages with "no LLM summarization, no truncation." Small, but in a 25k-test repo, marketing/docs divergence erodes trust. Keep ACUTE-CODE docs generated from the same source of truth as behavior.
- **Exact-pin-everything as the only supply-chain defense.** Defensible for a PyPI-distributed installer, but heavy maintenance; ACUTE-CODE should use standard lockfiles + audit tooling rather than hand-maintained `==` pins with per-CVE comments.
